# CI/CD — Finance Dashboard

> **Audience:** developer / maintainer (Claude or human).
> Everything the pipeline does, why it is shaped this way, and how to work on it.
> The pipeline itself is `.github/workflows/ci.yml`; this page explains it.

## What it does, in one paragraph

Every pull request, and every push to `main`, `develop`, `release/**` and
`hotfix/**`, builds the app on Windows and Linux, packages it into files an end
user can double-click, runs the tests and the linters, and uploads everything as
run artifacts. The project follows gitflow. A push to a `release/*` branch makes
CI open a pull request that opens the next version on `develop`. A push to
**`main`** is the merge of a `release/*` or `hotfix/*` branch, and it publishes a
GitHub release from those same files, with its tag. Then CI opens a pull request
that merges `main` back into `develop`. A push to `develop` or a `release/*`
branch, and a pull request with the label `experimental`, publishes a
pre-release of the Test app (§ Release channels). Nothing needs to be installed
by hand — including Qt, which the pipeline downloads for itself.

## The two rules the pipeline is built on

### 1. Jobs are independent

Every job checks out the repo, installs its own Qt, and reads the version itself.
No job `needs:` another, with three exceptions: `release` and `prerelease`
cannot run before the packages they publish exist, and **Open the next version
on develop** waits for the Changelog job, so that it never opens a pull request
from a broken `version.json`.

That costs a few minutes of duplicated setup per run and buys the thing that
matters when something breaks: **any single job can be re-run on its own** from
the GitHub UI, in isolation, without waiting on five unrelated jobs. A failing
linter cannot block a build, a broken Windows package cannot hide a Linux
regression, and debugging one job never means re-running the whole graph.

The shared setup lives in a composite action, `.github/actions/setup-qt`, not in
a job other jobs depend on. Same de-duplication, no dependency edge.

### 2. The version lives in exactly one file

`version.json` holds `current` — the version currently *in progress* — and the
whole changelog. Everything else reads from it:

| Consumer | How |
|---|---|
| The build | `CMakeLists.txt` does `string(JSON ... GET current)` before `project()` |
| The running app | `FD_VERSION_STRING` compile definition → `setApplicationVersion()` |
| Installers & archives | `CPACK_PACKAGE_VERSION`, and therefore every file name |
| The release tag | `v$(python tools/version.py current)` |
| The release notes | `python tools/version.py notes` |
| `version.md` | generated by `python tools/version.py render` |

A version number is never typed twice, so it can never disagree with itself.

On a pull request, its base branch is a second base (no change to the version of a release branch on `develop`); into `main`, the version must be dated; into `develop`, the version must not be in a release branch. ## How a build becomes something a user can run

The user asked for plug and play: download one file, run it, never think about
Qt. Every platform gets there through the same two steps.

### Step 1 — one self-contained install tree (CMake)

```sh
cmake --install build --prefix stage
```

`CMakeLists.txt` calls `qt_generate_deploy_qml_app_script()`, so this does far
more than copy a binary. Qt's own deployment API scans the built executable and
brings in every Qt library it actually links, the Qt plugins, the QML modules,
and a `qt.conf` pointing at them:

* **Windows** — drives `windeployqt`; the result is flat, `FinanceDashboard.exe`
  with its DLLs and `plugins/`, `qml/` beside it (`CMAKE_INSTALL_BINDIR` is set
  to `.` for exactly this).
* **Linux** — uses `file(GET_RUNTIME_DEPENDENCIES)` into `lib/`, `plugins/` and
  `qml/`, and rewrites the RPATH to `$ORIGIN/../lib`. System libraries (glibc,
  libGL, libX11) are deliberately left out.

This is the only place the question "which files ship?" is answered. Every
package below is cut from this one tree, so they cannot disagree.

Reference: <https://doc.qt.io/qt-6/cmake-deployment.html>

### Step 2 — wrap the tree

| Output | Built by | Notes |
|---|---|---|
| `-windows-x64.exe` (setup) | CPack `INNOSETUP` generator | Inno Setup 6, preinstalled on the `windows-2025` image; the job writes its version to the log. The setup asks "for me only" or "for all users", and makes a Start-menu shortcut, an optional desktop shortcut and an uninstaller. A newer setup updates an installed copy in place, because the `AppId` in `CMakeLists.txt` never changes. |
| `-windows-x64.zip` | CPack `ZIP` generator | Same tree, one folder deep. |
| `-linux-x86_64.tar.gz` | CPack `TGZ` generator | Run `bin/FinanceDashboard`. |
| `.AppImage` | `packaging/linux/make-appimage.sh` | AppDir + `AppRun` + `appimagetool`. |
| `.deb` | `packaging/linux/make-deb.sh` | `/opt/FinanceDashboard` + `/usr` desktop integration, built with `dpkg-deb`. |
| source `.tar.gz` / `.zip` | `git archive` | Respects `.gitignore` by construction. |

Both shell scripts take `<install-tree> <version> [output-dir]` and run fine by
hand on any Linux machine — that is the point of them being scripts rather than
workflow steps.

#### The Test app

`-DFD_APP_IDENTITY=test` (#130) builds "Finance Dashboard Test", which installs
and runs next to the prod app. `CMakeLists.txt` § App identity sets everything
that is different: the application name (so the data folder and the settings),
the window title, the icon, the Windows setup identity (`AppId`, install
folder, Start menu folder, shortcuts, uninstall entry) and the Linux desktop
entry and AppStream id. The executable is `FinanceDashboard` for both. CI
reconfigures the build directory of the prod app with the Test identity after
the prod packages are done, so only `main.cpp`, the icon resources and the QML
caches build again. The Test app has a setup, a ZIP and an AppImage
(`make-appimage.sh` reads the identity from the install tree); `make-deb.sh`
refuses a Test install tree. Its artifacts are `test-packages-windows` and
`test-packages-linux`, which the Release job does not collect: the pre-releases
use them (#129).

In the Test app, `main.cpp` also finds the prod database (the data folder of
the application name `FinanceDashboard`) for **Copy my prod database**
(`Database::replaceWithCopyOf()`, tested by `db_copy_test`).

#### Why not linuxdeploy / linuxdeployqt for the AppImage

Qt's CMake deployment already bundled the libraries, the plugins and the QML
modules and fixed the RPATHs in step 1. Running a second Qt bundler on top of
that duplicates the work and is the usual source of *"module X is not
installed"* at runtime. `make-appimage.sh` therefore only does the AppDir
wrapping — plus one thing Qt's deployment deliberately skips: it copies in the
small **xcb helper libraries** (`libxcb-cursor`, `libxkbcommon-x11`, …). Those
live in system directories so Qt's scan excludes them, but plenty of desktops
do not have `libxcb-cursor` installed, and its absence is the classic
*"could not load the Qt platform plugin xcb"* failure. The allowlist is at the
top of that block in the script.

#### Why not CPack's DEB generator

CPack installs under a single prefix. The `.deb` wants its payload in `/opt` and
four desktop-integration files in `/usr`, which would mean two CPack runs and a
component split — versus twenty readable lines of `dpkg-deb`.

Note the `.deb` bundles Qt rather than depending on the distribution's. That is
the plug-and-play trade-off, deliberately: it is *not* how a package accepted
into Debian proper would be built.

Qt's deployment leaves the system libraries out: glibc, X11/xcb, Wayland,
OpenGL/EGL, fonts, D-Bus and GLib. `make-deb.sh` therefore computes the
`Depends` line: it reads the `NEEDED` entries of the files that the app loads at
start-up (binary, bundled libraries, platform plugins and their integrations,
QML plugins, SQLite driver), keeps the libraries that are not bundled, and asks
`dpkg -S` which package installed each one on the build machine. Without these
packages, the `.deb` installs, then fails with *"could not load the Qt platform
plugin xcb"* on a machine that does not have them.

### Step 3 — prove it actually starts

Both packaging jobs run the app before uploading anything:

* **Windows** — launches the installed `.exe` with the real `windows` platform
  plugin and requires it to still be alive after 15 s. `main.cpp` calls
  `exit(-1)` on `objectCreationFailed`, so surviving means the whole QML tree
  loaded. The deploy step ships only the default platform plugin, so the
  `offscreen` plugin is not in the tree. After `cpack`, the job runs the setup
  silently twice (the second run is an update in place), then the uninstaller,
  for "for me only" (`/CURRENTUSER`) and for "for all users" (`/ALLUSERS`).
  Then the update from the app (#117): with the app running, the setup runs
  with the arguments of `UpdateInstaller::setupArguments()`. It must close the
  app (Restart Manager), install, and start it again
  (`packaging/windows/update-restart.iss`); a silent setup without
  `/RESTARTAPP=1` must not start it.
* **Linux** — runs the finished `.AppImage` under `Xvfb` with the real `xcb`
  platform plugin, same 20 s rule. Then `packaging/linux/test-deb.sh` installs
  the `.deb` in a clean `ubuntu:24.04` container, where only the package and its
  `Depends` are present: each library the app loads at start-up must be found,
  the app must stay up 20 s under `Xvfb`, and the package must remove cleanly.
  The runner itself cannot show a missing `Depends` entry, because the
  `setup-qt` action installed every X11 and GL library on it.

Before that, both jobs check that the install tree has the TLS backend of the
update check (#117, HTTPS): `tls/qschannelbackend.dll` on Windows (the TLS of
the system), `plugins/tls/libqopensslbackend.so` on Linux. The Linux backend
loads the `libssl.so.3` of the system at run time, with no `NEEDED` entry, so
`make-deb.sh` adds `libssl3t64 | libssl3` and `ca-certificates` to `Depends`
by name, and `test-deb.sh` checks that `libssl.so.3` is installed.

Both steps blank out `QT_PLUGIN_PATH`, `QML2_IMPORT_PATH` and the Qt entries in
`PATH`/`LD_LIBRARY_PATH` first. Without that the app would happily borrow a DLL
or a QML module from the builder's own Qt and the test would pass on a package
that is broken everywhere else.

## The release flow

The project follows gitflow. `develop` holds the in-progress version; `main`
holds released code only, and every merge into it publishes a release.

```
 develop: current = 0.2.2, no date
    │
    ├─ 1. cut          git switch -c release/0.2.2 develop, then push it
    │
 release/0.2.2 (CI, Open the next version on develop):
    ├─ 2. open next    branch chore/open-v0.2.3 from develop, version.py cut
    │                  → 0.2.3 in progress, 0.2.2 kept with no date
    │                  ("release in progress"); PR into develop, CI started
    │                  → merge it: develop takes changes for 0.2.3 again
    ├─ 3. fix          fixes for the release go into this branch, logged with
    │                  version.py add (under 0.2.2)
    ├─ 4. stamp        python tools/version.py release   → 0.2.2 dated today
    │                  commit "chore(release): v0.2.2", PR release/0.2.2 → main
    ├─ 5. merge        merge commit into main → CI runs on main
    │
 main (CI, release job, after every blocking job is green):
    ├─ 6. check        v0.2.2 has a date; is v0.2.2 already published?
    │                  (yes: skip 7–10; a draft is deleted and made again)
    ├─ 7. collect      download packages-windows / -linux / -source
    ├─ 8. checksums    sha256sum * > SHA256SUMS.txt
    ├─ 9. notes        version.py notes  +  .github/release-notes-footer.md
    ├─ 10. publish     gh release create v0.2.2 --target <sha> dist/*  (makes the tag)
    └─ 11. back-merge  branch chore/back-merge-v0.2.2 from develop, with main
                       merged into it (release_flow.py back-merge);
                       PR into develop, CI started on the branch
                       (each part skipped when it is already done)
```

CI commits nothing to `main` or `develop`. After you merge the back-merge pull
request, `develop` has the dated v0.2.2 and keeps the in-progress v0.2.3.

**Merge the pull request that opens the next version first.** From the cut to
that merge, v0.2.2 takes no new change on `develop`: a change merged in that
time would land under v0.2.2, and the release branch releases v0.2.2 without
it. So, while `release/<the version of develop>` exists, the Changelog job of a
pull request into `develop` fails. The version comes from `develop`, not from
the pull request: a pull request that renames the version does not pass. After
the merge, the job also refuses a pull request that changes v0.2.2
(`check --base origin/develop`). This occurs when the branch is older than the
cut: its entry is under v0.2.2. Update the branch from `develop` and move the
entry to v0.2.3.

**After the cut, update each open pull request into `develop`.** GitHub does
not run CI again when `develop` changes, and a re-run uses the merge commit of
the first run: a pull request that was green before the cut stays green. Update
its branch (the "Update branch" button) so that its CI runs again. If such a
pull request is merged anyway, the next push to the release branch fails in
**Open the next version on develop**: `develop` changed v0.2.2 after the cut.
Move the entry to the next version on `develop`, in a pull request.

**A release before that merge.** If v0.2.2 is released while the pull request
that opens v0.2.3 is still open, the back-merge opens v0.2.3 and the release
job closes that pull request. Merge the back-merge pull request first: until
then, the version of `develop` is released on `main`, and the Changelog job of
a pull request into `develop` fails.

**One release branch at a time.** `version.py cut` refuses a second one.
Release the first one and merge its back-merge pull request first.

**Dropping a release branch.** If a release branch is deleted with no release,
run `python tools/version.py uncut` on `develop` (in a pull request): v0.2.2 is
in progress again, with the entries of v0.2.3, and v0.2.3 is removed. Merge
into `develop` first the fixes of the release branch that you keep.

**The date** is stamped at the end of the release branch, just before the merge
into `main`: the date of a version is the day of its release. On a pull request
into `main`, the Changelog job refuses a version with no date
(`check --dated`).

**The back-merge pull request.** The release job opens it with `GITHUB_TOKEN`,
so GitHub must allow GitHub Actions to create pull requests (Settings →
Actions → General → Workflow permissions). If it cannot, the release is
published and the branch is pushed, but the job fails: change the setting,
then re-run the job. A pull request opened with `GITHUB_TOKEN` does not start
a CI run of its own, so the job starts one on the branch (`workflow_dispatch`,
the one event that `GITHUB_TOKEN` can start): its checks show on the pull
request, and a branch rule that asks for green CI can pass. Merge it with a
**merge commit**, not a squash: `develop` must contain the release commit of
`main`. The pull request into `develop` that opens the next version works the
same way.

**Why CI makes the merge.** At each release, `version.md` conflicts: both
branches change the heading of the released version. `version.md` is a
generated file, so `tools/release_flow.py` merges `main` into a branch from
`develop` and renders `version.md` again from the merged `version.json`, which
merges with no conflict. The pull request then has no conflict. If `develop`
did not open the next version (its pull request was not merged before the
release), the script opens the next patch, and the job closes that pull
request. A conflict in any other file stops the job after the release: merge by
hand (see the hotfix commands below), then re-run the job. The job also stops
when the merge changes a version that is released on `main`: `develop` changed
it after the cut. Fix `develop` first, then re-run the job.

**Re-running the release job.** A re-run (Actions → the run → Re-run failed
jobs) finishes what the earlier run started, and does each part only once. A
published release is not published again; a draft that a stopped upload left
is deleted and published again. The back-merge is skipped when `develop`
already contains the release commit, and the branch and the pull request are
not made twice. If the tag `vX.Y.Z` exists on another commit, the job stops.

**One release job at a time.** Each run on `main` has a concurrency group of
its own, so no run on `main` cancels another one. The release jobs share the
`release` group with `queue: max`: they publish one at a time, in the order
they arrive. With the default queue, a release job that waits would be
cancelled when a third one arrives.

**Minor and major releases.** The cut opens a patch. To make the in-progress
version a minor or a major one, run on `develop`:

```sh
python tools/version.py bump minor   # in-progress 0.2.3 → 0.3.0, its entries kept
git commit -am "chore: make the in-progress version v0.3.0"
```

`bump` renames an in-progress version instead of adding a second one: only the
current version and the version of a release branch can be undated. It counts
from the highest other version: the latest release, or the version of the
release branch.

**Hotfixes.** `hotfix/<x.y.z>` starts from `main`: run `version.py bump patch`
(the patch after the released version), commit the fix, run
`version.py release`, then merge into `main`. The release job publishes it.
Its back-merge stops on a conflict in `version.json`: both branches add a
version at the top. If `develop` uses the same number for its in-progress
version, renumber `develop` first (`version.py bump minor`). Then merge by hand.
Do not start a hotfix while a release branch is open: it would take the number
of the release branch. Put the fix into the release branch, and release it.

```sh
git switch -c chore/back-merge-v0.2.2 origin/develop
git merge --no-ff origin/main     # version.json: keep develop's current version, add the released one below it
python tools/version.py render    # version.md
python tools/version.py check --base origin/main
git add version.json version.md && git commit --no-edit --cleanup=strip
git push -u origin HEAD           # pull request into develop, merged with a merge commit
```

**Branch protection.** CI never pushes to `main` or `develop`, so a branch rule
needs no bypass for `github-actions[bot]`.

## Release channels

Three channels, each published by CI as GitHub releases (#129). The prod app
gets the releases; the Test app (`-DFD_APP_IDENTITY=test`, see § The Test app)
gets the pre-releases.

| Channel | Built from | Tag | GitHub release | App |
|---|---|---|---|---|
| Experimental | each push to `develop`; each run of a pull request with the label `experimental` | `v0.2.2-exp.<run>`, `v0.2.2-exp.<run>.pr<number>` | pre-release | Test |
| Preprod | each push to `release/*` | `v0.2.2-rc.<run>` | pre-release | Test |
| Prod | each merge into `main` | `v0.2.2` | latest release | Prod |

`0.2.2` is the version of `version.json`, and `<run>` is the run number of the
workflow (`github.run_number`): the same in every job and every re-run of a
run, and higher for each new run. The suffixes follow SemVer, so the versions
sort in build order, and every experimental build comes before every release
candidate of the same version: `0.2.2-exp.57 < 0.2.2-exp.61.pr12 <
0.2.2-rc.70 < 0.2.2`. The updater (#117) can compare them.

`tools/release_flow.py channel` computes the channel, the suffix and the tag of
a run. The packaging jobs pass the suffix to the Test build
(`-DFD_VERSION_SUFFIX=-exp.57`): it goes into the version of the app, the
`AppVersion` of the setup and the file names. A pull request without the label
gets the suffix too (`-exp.<run>.pr<number>`), so that its Test packages are
the ones the label would publish, but nothing is published. The prod packages
never have a suffix.

The **Pre-release** job downloads the Test packages, checks that their file
names have the version, writes `SHA256SUMS.txt` and publishes a pre-release
with its tag: on the commit of the run, or for a pull request on its head
commit (CI built the merge of that commit into the base branch, and the notes
say so). The notes: for `-rc`, the changelog of the version in progress; for
`-exp`, the branch, the commit and the pull request; then, for both,
`.github/prerelease-notes-footer.md`. Then the job deletes the published
experimental pre-releases after the 10 newest, with their tags. The Release
job deletes the `-rc` pre-releases of a version when it publishes that
version. A re-run does not publish twice. If the tag exists on another
commit, the job stops: delete the tag, then re-run the job.

**A burst of pushes.** A new push cancels the run in progress on the same
branch, so only the last push of a burst publishes.

**Publish a pull request.** Add the label `experimental`: the run that the
label starts publishes the pre-release, and each later push publishes a new
one. Another label also starts a run (GitHub runs CI on `labeled`), which
publishes nothing. A pull request from a fork never publishes: its token
cannot write.

## Working with the changelog

`version.md` is now **generated**. Edit `version.json`, or better, use the tool:

```sh
python tools/version.py add Added "`Foo.qml` — what it does."
python tools/version.py add Fixed "Bar no longer does the wrong thing."
python tools/version.py add Added --group "Navigation & shell" "..."
python tools/version.py summary "One line describing this version."
python tools/version.py render          # refresh version.md (add/summary/bump/cut/release do it too)
python tools/version.py check --base origin/main   # what CI runs
python -m unittest discover -s tools -p "test_*.py" # the tests of the tools, also run by CI
```

The maintenance rule is unchanged — log the change when you make it, under the
current in-progress version. Only the command is new. If you do edit
`version.json` by hand, run `render` afterwards or the Changelog job fails.
`add` and `summary` refuse to change a released (dated) version. `cut` and
`uncut` are for the release flow: CI runs `cut` (through
`tools/release_flow.py`) when a release branch is cut, and `uncut` undoes it
when a release branch is dropped.

## Changing things

**Bump Qt.** One line, `QT_VERSION` in `.github/workflows/ci.yml`. Available
versions: <https://download.qt.io/online/qtsdkrepository/>.

Check that aqtinstall can actually fetch the version you pick, though — the
pipeline gets Qt from aqt, not from the Qt installer, and aqt has to be taught
each change to Qt's repository layout. Qt 6.11.0 moved the Windows packages
from `windows_x86/desktop/qt6_<ver>/qt6_<ver>/` to a per-compiler
`qt6_<ver>_msvc2022_64/`, and aqtinstall 3.3.0 still requests the old path:

```
ERROR : Failed to locate XML data for Qt version '6.11.2'.
```

Linux kept the flat layout, so a version bump can break Windows alone and look
like a Windows problem. `QT_VERSION` is therefore pinned to **6.10.3** until
[aqtinstall #959](https://github.com/miurahr/aqtinstall/issues/959) (fixed by
PR #1000) reaches a release; then it goes back to 6.11.x with a one-word edit.
The project itself needs Qt 6.10+, so this is purely a tooling constraint — it
does not affect what the app can use, and developing locally against a newer Qt
than CI builds with is fine.

To check a layout before bumping, look for
`.../qt6_<version-without-dots>/` under
`windows_x86/desktop/` and `linux_x64/desktop/` and see whether the folder
inside it repeats the name or carries a compiler suffix.

**Adding a Qt module.** `QT_MODULES` must list not just the modules the app
uses but everything *those* modules depend on — aqt installs exactly what you
name and resolves nothing. Qt Graphs is the example: the binary Qt ships it
built with both the 2D and 3D features on, so it lists `Qt::Quick3D` as a public
link dependency and `Qt6GraphsConfig.cmake` calls `find_dependency(Qt6Quick3D)`.
Install `qtgraphs` alone and CMake says:

```
Failed to find required Qt component "Graphs".
  Expected Config file at ".../Qt6Graphs/Qt6GraphsConfig.cmake" exists
```

Read that carefully — *exists*. The component is installed; one of its
dependencies is not. Hence `QT_MODULES: qtgraphs qtquick3d qtshadertools`.

The composite action's **Verify the Qt CMake packages this project needs** step
exists for exactly this: it checks each `Qt6<Component>Config.cmake` right after
install and, when one is absent, names it and lists everything that *was*
installed — five seconds, and an error that says what to add. Add any new
`find_package(Qt6 COMPONENTS ...)` entry to that step's list too.

**Turning the linters into gates.** `qmllint` and `clang-tidy` are
`continue-on-error: true` because neither has ever run over this codebase in CI
and a first-run wall of warnings must not block releases. Once a tree is clean,
delete that line from its job — nothing else changes.

**Add macOS.** Copy `package-windows`, switch the runner to `macos-14`, drop the
Inno Setup steps. `qt_generate_deploy_qml_app_script()` already handles `.app` bundles
via `macdeployqt`, so CPack `DragNDrop` gives a `.dmg`. Nothing outside that new
job needs to change — that is the independence rule paying off. (Unsigned macOS
builds are refused by Gatekeeper, so read the code-signing note below first.)

**Older Linux distributions.** Builds run on ubuntu-24.04, so the binaries need
glibc ≥ 2.39 (Ubuntu 24.04+, Debian 13+, Fedora 40+). ubuntu-22.04 runners are
being retired, so the way to widen that is `container: ubuntu:22.04` on the
Linux packaging job rather than an older runner label.

**Code signing.** Nothing is signed, so Windows SmartScreen warns on first run
and macOS would refuse outright. Signing needs a certificate in repository
secrets plus a `signtool` step after `cpack`; worth doing only if this is ever
distributed beyond you.

## Running the whole thing locally

```sh
# Linux
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DFD_BUILD_TESTS=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
cmake --install build --prefix stage
( cd build && cpack )                                          # .tar.gz
bash packaging/linux/make-appimage.sh stage "$(python3 tools/version.py current)" dist
bash packaging/linux/make-deb.sh      stage "$(python3 tools/version.py current)" dist
deb=$(ls dist/*.deb); docker run --rm -v "$PWD:/src:ro" ubuntu:24.04 \
    bash /src/packaging/linux/test-deb.sh "/src/$deb"      # clean-system test
```

```powershell
# Windows (the setup needs Inno Setup 6 and CMake >= 3.27)
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release --parallel
cmake --install build --config Release --prefix stage
cd build ; cpack -C Release                                    # setup .exe + .zip
```

`act` is not worth setting up for this pipeline — the jobs are mostly "install
Qt, build, package", and the local commands above reproduce them exactly.
